## 1. 目的

通过统一分支、提交信息、Pull Request（PR）和代码审查要求，降低缺陷进入主分支的概率。所有合并到主分支的代码必须可追踪、可复现、可回滚。

## 2. 分支策略

| 分支 | 用途 | 规则 |
|---|---|---|
| `main` | 稳定主分支 | 禁止直接推送，必须经 PR |
| `develop` | 集成测试分支 | 通过 CI 后合并 |
| `feature/<name>` | 新功能开发 | 从 develop 创建 |
| `fix/<name>` | 普通缺陷修复 | 描述问题和修复方式 |
| `hotfix/<name>` | 紧急修复 | 修复后同步回 develop |

分支名使用小写英文和连字符，例如 `feature/document-upload`。

## 3. Commit Message 规范

建议格式：

```text
<type>(<scope>): <short summary>
```

常用 type：

| type | 含义 | 示例 |
|---|---|---|
| feat | 新功能 | `feat(rag): add hybrid retrieval` |
| fix | 缺陷修复 | `fix(api): handle empty query` |
| docs | 文档变更 | `docs(readme): update setup guide` |
| test | 测试变更 | `test(retriever): add recall cases` |
| refactor | 重构 | `refactor(loader): separate parsers` |
| chore | 构建或杂项 | `chore(deps): pin package versions` |

提交摘要使用祈使或简洁动作描述，避免“修改一下”“最终版”等不可检索表述。

## 4. Pull Request 要求

PR 必须说明：

1. 变更背景和目标。
2. 主要实现内容。
3. 影响的 API、数据库表、配置和依赖。
4. 本地测试命令及测试结果。
5. 是否涉及数据迁移或回滚。
6. 是否新增、修改或删除环境变量。

关联 E002 的接口变更必须同步更新 OpenAPI 文档和测试。

## 5. 审查检查清单

### 5.1 正确性

- [ ] 业务逻辑符合需求。
- [ ] 边界条件和异常路径已处理。
- [ ] 空输入、重复请求和并发场景有明确行为。
- [ ] 数据库事务和资源释放正确。

### 5.2 安全性

- [ ] 没有提交 `.env`、API Key、密码或令牌。
- [ ] 日志没有输出敏感信息。
- [ ] 用户输入经过校验。
- [ ] 文件上传限制大小和类型。
- [ ] 权限检查位于可信的服务端。

### 5.3 可维护性

- [ ] 函数和变量命名清晰。
- [ ] 复杂逻辑有必要的注释。
- [ ] 没有无用代码、调试输出和硬编码路径。
- [ ] 依赖变更有理由并记录版本。

### 5.4 RAG 专项

- [ ] Chunk 元数据包含 document_id、source 和 chunk_index。
- [ ] 文档删除时能清理对应向量。
- [ ] 检索结果不会跨越无权限的租户边界。
- [ ] 引用片段确实来自检索到的文档。
- [ ] 无依据时系统能拒答，而不是编造来源。

## 6. 自动化质量门禁

合并前至少运行：

```bash
python -m compileall app
pytest -q
```

如果项目配置了格式化、静态检查或类型检查工具，还应运行对应命令。CI 失败时不得通过删除测试或跳过检查来绕过问题。

## 7. 代码审查角色

- 作者：自测、填写 PR 描述、回应审查意见。
- 审查者：检查正确性、安全性和可维护性。
- 合并负责人：确认 CI 通过、必要审批完成后合并。

演示项目可采用至少一名审查者的规则；该规则是模拟流程，不代表真实组织制度。

## 8. 紧急修复

紧急修复也必须保留提交记录和测试证据。修复完成后应同步到长期开发分支，并补充故障记录。生产事故处置参照 E006。
