## 1. 目的与数据职责

本规范定义关系数据、缓存数据和向量数据的使用边界。

- PostgreSQL：用户、文档登记信息、任务状态和结构化业务数据。
- Redis：短期缓存、限流计数和可重建的临时状态。
- Qdrant：文档 Chunk 的向量表示及检索元数据。

向量数据库不是业务主数据的唯一来源。原始文档和必要元数据应保存在受控存储中，以便重建索引。

## 2. 数据建模原则

- 表名和字段名使用小写 `snake_case`。
- 每张业务表应定义主键。
- 对常用筛选和关联字段建立经过评估的索引。
- 记录创建时间和更新时间。
- 对可删除数据定义明确的级联或清理策略。
- 不在数据库中存储明文密码或不必要的秘密。

示例逻辑表：

| 表名 | 主要字段 | 用途 |
|---|---|---|
| `documents` | `id`, `file_name`, `status`, `created_at` | 文档登记 |
| `ingestion_jobs` | `id`, `document_id`, `status`, `error_code` | 导入任务 |
| `conversations` | `id`, `user_id`, `created_at` | 会话信息 |
| `messages` | `id`, `conversation_id`, `role`, `content` | 会话消息 |

以上为逻辑示例，不代表已经提供数据库迁移脚本。

## 3. 连接管理

- 使用连接池，避免每个请求都创建独立数据库连接。
- 为连接和查询设置合理超时。
- 在请求结束时正确归还连接。
- 使用参数化查询或 ORM，禁止拼接不可信输入形成 SQL。
- 连接串通过环境变量注入，参照 E001。

## 4. 事务要求

涉及多个相关写操作时，应评估是否需要事务。事务应尽可能短，避免在事务中调用慢速外部模型 API 或执行耗时文件解析。

推荐流程：先在数据库中登记导入任务，再在事务外完成解析和 Embedding，最后用短事务更新任务状态和索引信息。失败时记录可重试状态，避免长事务占用连接。

## 5. Redis 使用规范

- 设置与业务相符的 TTL。
- 缓存键应包含业务前缀和必要的租户隔离信息。
- 不将 Redis 当作永久数据存储。
- 缓存失效时，系统应能从主数据源恢复。
- 限流计数和会话状态应设置合理过期时间。

示例键：`nebula:ratelimit:<USER_ID>:<WINDOW>`。尖括号内容为占位符。

## 6. Qdrant 向量索引规范

每个 Point 至少应保存可追踪的 `document_id`、`chunk_index`、`source` 和必要的分类字段。向量维度必须与所使用的 Embedding 模型输出一致。

- Collection 的向量配置应记录模型名、维度和距离度量。
- 更换 Embedding 模型或维度时，不应直接把新旧向量混在同一配置中。
- 文档更新时应清理旧 Chunk，再写入新 Chunk，或采用可验证的版本化策略。
- 删除文档时，必须按 `document_id` 删除对应向量。
- 检索时应用权限过滤，避免返回用户无权访问的内容。

## 7. 备份与恢复

演示环境建议定期执行数据库备份，并在重要变更前创建备份。备份文件应限制访问并加密存储。恢复演练应记录恢复时间、数据完整性和失败情况。

具体保留周期需根据部署环境、数据分类和业务要求确定；本模拟文档不设定真实合规保留期限。

## 8. 慢查询与容量

发现慢查询时，应检查执行计划、索引命中、扫描行数和连接池等待。不得仅通过无限增加连接数解决性能问题。容量告警应结合 CPU、内存、磁盘、连接数和查询延迟综合判断。
